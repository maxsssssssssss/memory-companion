# QA JSON Schema Optimization Analysis

Date: 2026-07-23

## Executive conclusion

The current QA Provider response is already close to a minimal contract. The
model is asked to generate only:

```json
{
  "mode": "assistant_meta | memory_answer | unsupported",
  "answer": "回答正文，并在事实句后附 [E1]",
  "citationIds": ["E1"]
}
```

The model does **not** generate citation objects, source segment IDs, time
ranges, scope metadata, owner metadata, confidence fields, validation results,
or persistence fields. Those values are derived on the server from canonical
Evidence.

Consequently, the proposed `{ answer, citationIds }` contract removes only
`mode`. That saves little output while weakening the explicit
`assistant_meta / memory_answer / unsupported` safety route. It is not the
recommended experiment.

A safer experiment is:

```json
{
  "mode": "memory_answer",
  "answer": "每个事实句继续携带 inline [E1]"
}
```

In other words, retain `mode` and sentence-local citations, but omit the
response-level `citationIds` array because the server can already derive it
from inline citations. This is worth a small evaluation-only A/B test, but it
is not expected to fix the main QA latency bottleneck. A realistic expectation
is approximately `0–5%` generation-latency improvement and almost no raw TTFT
improvement.

## 1. Current response contract

### 1.1 Model-generated wire response

`StructuredAiAnswer` contains only three fields:

| Field | Generated by model | Purpose |
| --- | --- | --- |
| `mode` | Yes | Routes assistant metadata, grounded memory answers, and unsupported answers |
| `answer` | Yes | User-facing answer; factual sentences carry inline `[E#]` citations |
| `citationIds` | Yes | Response-level list of Evidence IDs cited by the answer |

The Agent and Direct prompts request the same three-field JSON contract. The
Provider call does not use `response_format` or a formal Provider-side JSON
Schema; it requests ordinary text and the server performs conservative parsing
afterward.

The parser:

1. removes an optional JSON code fence;
2. calls `JSON.parse`;
3. validates the `mode` enum;
4. requires a non-empty string `answer`;
5. keeps string entries from `citationIds`;
6. rejects malformed structures and falls back through the existing safe path.

Relevant implementation:

- `src/lib/server/retrieval/ai-qa.ts`: `StructuredAiAnswer`,
  `buildHumanizedQaSystemPrompt()`, and `parseStructuredAiAnswer()`;
- `src/lib/server/retrieval/qa-provider.ts`: Chat/Responses request and
  streaming adapters.

### 1.2 Server-generated final object

The larger `QuestionAnswer` object is not the LLM response schema. The server
creates these fields deterministically:

| Final `QuestionAnswer` field | Source |
| --- | --- |
| `id` | Server UUID |
| `uploadId` | Current request |
| `question` | Current request |
| `answer` | Validated model answer or deterministic fallback |
| `citedSegmentIds` | Canonical Evidence mapping |
| `citations[].id` | Validated `E#` allowlist |
| `citations[].title` | Canonical Evidence |
| `citations[].startSeconds/endSeconds` | Canonical Evidence |
| `citations[].excerpt` | Canonical Evidence projection |
| `citations[].sourceSegmentIds` | Canonical Evidence |
| `createdAt` | Server timestamp |

Relationship confidence/caution boundaries are also restored from canonical
cited Evidence when necessary. Scope, lifecycle intent, owner attribution, and
validation diagnostics are server-side context or checks; the model does not
need to repeat them as JSON fields.

## 2. Retained-output size analysis

### 2.1 Measurement method and limitation

The retained `long-recording-60m` reports intentionally do not store the raw
Provider JSON response. They store the validated final answer, citation/source
metadata, and latency measurements.

Therefore, the measurements below reconstruct a minified response using the
current three-field contract from the 21 completed GPT-5.5 Original Evidence
arm runs in the Compact Evidence A/B benchmark. They are representative
contract sizes, not exact byte-for-byte Provider responses. They cannot measure
Provider whitespace, code fences, unknown extra fields, or exact billed output
tokens.

The project convention `ceil(characters / 2)` is shown only as a rough token
estimate. Chinese text and JSON keys can tokenize differently.

### 2.2 Typical response

Across 21 Original Evidence runs:

| Metric | Value |
| --- | ---: |
| Final answer text, mean | 138.1 chars |
| Final answer text, median | 106 chars |
| Final answer text, range | 74–267 chars |
| Reconstructed JSON, mean | 207.1 chars |
| Reconstructed JSON, median | 175 chars |
| Reconstructed JSON, P95 | 350 chars |
| Reconstructed JSON, range | 136–352 chars |
| Rough reconstructed tokens, mean | about 104 |

Field contribution includes each field name, colon, and encoded value:

| Part | Mean chars | Share |

| Braces/commas | 4.0 | 1.9% |

The answer text is already the dominant output. There is no large nested
metadata object to remove.

### 2.5 What the latency data implies

Across the full Original arm, mean TTFT was `6,824 ms` and mean generation
latency was `9,620 ms`. Only about `2,796 ms` occurred after the first Provider
delta.

Answer length correlated strongly with this post-TTFT output phase in the
42-run benchmark, but not with total generation latency. This is consistent
with Provider reasoning/input processing dominating total latency while output
length mainly affects the smaller stream tail.

## 3. Simplification options

### Option A: `{ answer, citationIds }`

This is the originally proposed contract.

#### What it actually removes

Relative to the current implementation, it removes only:

```json
"mode": "memory_answer"
```

The reduction is a fixed `23` minified characters per normal response,
approximately `11%` of the reconstructed average JSON.

#### Feasibility

The server could attempt to infer mode from query intent and answer wording,
but this would not preserve current behavior:

- `assistant_meta` distinguishes questions about the assistant from questions
  about local memories;
- `unsupported` triggers grounded deterministic handling;
- q022/q034-style lifecycle boundaries rely on distinguishing a commitment
  from evidence of completion;
- wording-based unsupported detection is weaker than an explicit enum.

#### Expected latency

A crude linear model applied only to the post-TTFT output phase suggests
roughly `0–0.3 seconds` potential reduction. Raw TTFT is measured at the first
Provider delta, normally the opening JSON token, so it should remain almost
unchanged.

#### Recommendation

Do not choose this as the first experiment. The small reduction does not
justify weakening explicit safety routing.

### Option B: `{ mode, answer }` with mandatory inline citations

This retains the safety-critical mode while removing the response-level
`citationIds` array.

#### Feasibility

This is technically compatible with the current architecture:

- every factual sentence continues to contain inline `[E#]`;
- the finalizer can already derive effective citation IDs from the answer;
- citation objects and source segment IDs remain server-generated;
- the canonical Evidence allowlist remains unchanged;
- malformed or unknown inline IDs continue to fail closed.

The Original-arm reconstruction suggests a mean reduction of about `32.7`
characters (`15.8%` of the response). Depending on citation count, typical
savings are approximately `26–36` characters.

#### Risk

The global `citationIds` list currently provides redundant response-level
metadata. Removing it makes inline sentence citations the sole model-provided
mapping. The existing Sentence Commit checks are strong enough to validate that
mapping, but regression coverage must prove:

- every factual sentence retains local support;
- all IDs belong to the current Evidence allowlist;
- inline IDs, server citation objects, and `citedSegmentIds` remain aligned;
- missing or invalid citations are visible failures, not hidden fallbacks.

#### Expected latency

A linear post-TTFT estimate gives approximately `0–0.45 seconds`, or roughly
`0–5%` of total generation latency. Actual token savings may be smaller because
the ASCII JSON field name compresses efficiently.

This is the recommended evaluation-only candidate.

### Option C: plain answer text with inline citations

Example:

```text
陶艺预约已经提交并确认。[E1]
```

This removes all JSON routing. It is smaller, but it loses the explicit mode,
increases ambiguity around unsupported answers, and changes parser/fallback
behavior. It should not be used for the first experiment.

## 4. Streaming impact

Current flow:

```text
Provider token stream
        |
        v
partial answer candidates (quarantined)
        |
        v
complete Provider response
        |
        v
mode / citation / lifecycle / owner validation
        |
        v
canonical QuestionAnswer
        |
        v
SentenceCommitManager
        |
        v
validated sentence events
```

`SentenceCommitManager.ingestDelta()` can identify sentence-shaped candidates
inside the partial JSON `answer` value, but those candidates remain
`validated:false` and `safeForSpeech:false`.

The system emits committed sentences only after:

1. the complete Provider stream finishes;
2. the JSON or plain-text response passes normal QA finalization;
3. canonical citation objects are built;
4. inline citation IDs, citation metadata, support IDs, and
   `citedSegmentIds` match;
5. the whole response is fully committable.

As a result, a smaller JSON response can finish slightly sooner, but it does
not change the current safety boundary or overlap LLM generation with TTS.

Expected effects:

| Metric | Expected effect |
| --- | --- |
| Raw TTFT | Approximately unchanged |
| First natural-language answer token | At most a few tokens earlier if field order changes |
| Stream completion | Slightly earlier |
| Full validation completion | Slightly earlier |
| First safe sentence | Slightly earlier, bounded by stream-tail savings |
| TTS start | Same small downstream improvement |

Meaningful early speech would require a separately designed incremental
validation protocol. Reducing JSON alone cannot safely provide that behavior.

## 5. Safety analysis

### Citation validation

The model does not need to generate citation objects. It only needs valid `E#`
references. The server can map those references back to canonical Evidence.

However, a global list such as:

```json
["E1", "E3"]
```

is not sufficient for current sentence-level streaming safety. Each factual
sentence must retain its own inline citation so the system can determine which
support IDs ground that sentence.

### Evidence First and source mapping

These remain safe if:

- Evidence IDs are selected from the current allowlist;
- canonical Evidence remains the only source of transcript/source IDs;
- the model never generates source segment IDs;
- final citation objects continue to be server-generated;
- the whole-response fail-closed rule remains unchanged.

### Lifecycle correctness

No lifecycle metadata needs to be generated by the model. Lifecycle intent,
ranking, and grounded unsupported handling are server-side. The `mode` field
should remain because it explicitly signals when the model considers completion
unsupported.

### Owner attribution

Owner metadata is supplied as constrained context and checked by server
boundaries. The model should not generate a new owner object. Minimal JSON does
not change this as long as owner-boundary validation remains identical.

### Relationship confidence and caution

Confidence/caution are properties of canonical Relationship Evidence, not
required response fields. The server already restores missing boundaries from
cited Evidence. Removing output fields that do not currently exist provides no
additional benefit.

### Unsupported handling

This is the strongest reason to retain `mode`. Removing it would require
heuristic interpretation of arbitrary answer wording and could turn a grounded
“completion cannot be confirmed” response into a generic fallback.

## 6. Recommended A/B benchmark

### Compared contracts

Current:

```json
{
  "mode": "memory_answer",
  "answer": "事实句。[E1]",
  "citationIds": ["E1"]
}
```

Minimal-safe:

```json
{
  "mode": "memory_answer",
  "answer": "事实句。[E1]"
}
```

### Controlled variables

Keep identical:

- model and Provider;
- wire API and temperature;
- question and execution order policy;
- canonical Evidence and Evidence digest;
- Memory and Relationship context;
- system/safety instructions, except the output-format sentence;
- lifecycle retrieval and unsupported handling;
- final citation/source validation;
- Sentence Commit and Voice Response Optimizer.

The minimal arm must not silently retry with the current schema. A malformed or
unsafe minimal response must be reported as a minimal-contract failure.

### Test set

At minimum:

- q017: plan to completion;
- q018: unresolved choice to final decision;
- q022: grounded unsupported completion;
- q034: partial fulfillment versus “all completed”;
- preference ownership;
- relationship communication rules;
- ordinary multi-sentence summary;
- assistant identity question;
- deliberately missing and invalid inline citation fixtures.

Use serialized, counterbalanced execution with enough rounds to distinguish a
likely `0.3–0.5 second` effect from Provider/network variance. The previous
benchmark showed variance larger than the expected saving, so three rounds
should be treated as exploratory rather than decisive.

### Metrics

Performance:

- raw Provider response characters;
- Provider-reported output tokens when available;
- raw TTFT;
- time to first `answer` content delta;
- stream completion;
- response validation;
- first safe sentence;
- generation and total latency.

Safety and quality:

- JSON parse success;
- valid mode routing;
- missing/invalid inline support;
- citation allowlist validity;
- citation metadata/source alignment;
- lifecycle correctness;
- owner-boundary correctness;
- unsupported correctness;
- sentence units and committed units;
- fallback reason and final source.

### Acceptance criteria

Consider a production gray only if:

1. paired latency data shows a repeatable improvement beyond normal variance;
2. citation and source mapping remain fully valid;
3. q017/q018/q022/q034 do not regress;
4. unsupported and assistant-meta routes remain explicit;
5. no minimal-contract failure is hidden by legacy fallback;
6. streaming commit coverage does not decrease.

## 7. Final recommendation

Reducing QA JSON complexity is **not a high-priority latency optimization**
because the current contract is already minimal and Provider TTFT dominates
generation time.

- Do not implement `{ answer, citationIds }` as proposed; it removes the
  safety-critical field and retains the more redundant field.
- A small evaluation-only `{ mode, answer }` A/B is reasonable because it
  preserves explicit routing and lets the server derive citation metadata from
  sentence-local `[E#]`.
- Expect low single-digit generation improvement, not a major reduction in
  voice response latency.
- Continue prioritizing Provider reasoning/TTFT, Evidence selection, and context
  size for material latency gains.

No production schema, Provider behavior, retrieval logic, or validation rule
was changed as part of this analysis.
